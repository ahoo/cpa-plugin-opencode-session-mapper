# Troubleshooting sessions, API compatibility, and access

Reviewed on **2026-10-21**. Endpoint behavior, model availability, and free-tier
policy can change; use the linked official documentation for current setup.

## What Issue #5 establishes

[Issue #5](https://github.com/ahoo/cpa-plugin-opencode-session-mapper/issues/5)
reports HTTP 403 with:

> OpenCode's free tier can only be used from within OpenCode

That indicates an upstream free-tier access / request-validation rejection,
not the `MissingSessionID` error this plugin's session mapping can address.
The report does not include the model ID, client/host/plugin versions,
upstream URL, credential mode, or a sanitized wire capture. We therefore
cannot identify the exact failed check or claim to have reproduced that
installation. A missing session header could coexist with the rejection,
but the 403 text alone does not prove it.

The code reviewed was session-mapper
[`f883240`](https://github.com/ahoo/cpa-plugin-opencode-session-mapper/tree/f88324094c3c3e55b0287da886a749aa57063773)
(source version `0.3.2`). In
[`main.go`](https://github.com/ahoo/cpa-plugin-opencode-session-mapper/blob/f88324094c3c3e55b0287da886a749aa57063773/main.go),
`interceptHeaders` returns header additions only. It preserves an existing
`X-Opencode-Session`, maps recognized session sources, and falls back to
`Metadata.canonical_session_id` when eligible. The decoded payload deliberately
omits `Body`. There is no URL/protocol rewrite, credential generation, or
free-tier access implementation.

## Separate the three layers

| Layer | Evidence to inspect | Plugin responsibility | Next action |
|---|---|---|---|
| Session propagation | `MissingSessionID` (historically HTTP 400); missing or changing `X-Opencode-Session` on the actual outbound request | Map a valid session source and let the host forward it | Check loading, source headers / metadata, and credential `headers:` references |
| API compatibility | Wrong API path/family, unsupported model, message/tool schema, streaming or token-limit error | None; the plugin does not transform these fields | Match the current official endpoint and schema; investigate client / host translation |
| Access and quota | Explicit free-tier rejection, credential/permission error, or quota-exhaustion response | None; session and client labels confer no entitlement | Use an officially supported route and eligible account/model; escalate a supported-route rejection upstream |

HTTP status alone is insufficient. A 403 can arise from request classification
or permission checks; it does not necessarily mean quota exhaustion. Keep the
upstream error type/message and distinguish it from an error generated by the
proxy. Likewise, a successful header-mapping test does not prove inference is
authorized.

## Officially supported access

The [current Inference API documentation](https://opencode.ai/v2/docs/console/api/inference/)
documents `/inference` with API-family-specific paths. For example, Chat
Completions uses `/inference/openai/v1/chat/completions`. It explicitly permits
free chat calls without an API key; paid calls require a Console personal or
service-account key. Use the
[model endpoint table](https://opencode.ai/v2/docs/console/models/#endpoints)
for the selected model.

Do not turn the older 403 message into a blanket claim that all free models
are permanently unavailable outside OpenCode. Documented keyless API support
also does not guarantee that every model, older path, or arbitrary request
will pass the service's checks.

For use in OpenCode, select an available model with `/models` in the current
official client. For other coding agents, follow the
[official harness setup](https://opencode.ai/v2/docs/console/harnesses/),
including the plan, credentials, protocol, and model it supports. If an offer
is restricted to OpenCode, use it there; otherwise use the documented API
under that offer's terms or an authorized paid/provider integration.

An API key does not by itself remove free-model eligibility or quota limits.
Do not change `cliproxy` to a fabricated official-client identity, manufacture
request identity headers, inject fake tools, or weaken tool permissions just
to defeat a rejection. A session ID is a routing signal, not authorization.

Official-client users have also reported this message in
[OpenCode issue #49678](https://github.com/anomalyco/opencode/issues/49678).
Those reports show that the wording alone cannot establish that a caller is
outside OpenCode; they do not prove a particular cause for Issue #5. If the
documented API or current official client still fails, report the sanitized
request details to OpenCode rather than treating this plugin as a bypass.

## What the separate gateway tested

[ahoo/opencode2api PR #1](https://github.com/ahoo/opencode2api/pull/1) was
merged on **2026-10-14**, at
[`794546b`](https://github.com/ahoo/opencode2api/tree/794546b6086b7929d216b9b3ac8be51bb61643ea),
also the gateway's `main` revision at this review.

Its author reported controlled live replays in which the legacy `/zen`
anonymous route returned 403, while the `/inference` route also checked
request identity and message/tool format. The gateway changed anonymous
routing, identity handling, and request preparation; it left keyed routing
unchanged. These functions are in the gateway's
[`internal/gateway/upstream.go`](https://github.com/ahoo/opencode2api/blob/794546b6086b7929d216b9b3ac8be51bb61643ea/internal/gateway/upstream.go),
not in session-mapper.

The PR reports HTTP 200 for `space-bunny-free`, `mimo-v2.6-flash-free`, and
`cat-jam-free`, with both SSE and collapsed JSON results, plus build/vet and
health-check success. These are historical, author-reported results for that
gateway and those test conditions. They were not rerun in this documentation
review and are neither a current availability guarantee nor evidence of
official authorization.

Consequently:

- The gateway PR did not patch, release, or validate session-mapper.
- Replacing `/zen` with `/inference` alone was not the entire gateway change.
- Its historical `/inference/v1/...` description is not a substitute for the
  current official API-family paths.
- This documentation update clarifies scope; it does not fix or claim to
  resolve the reported free-tier 403.

## Check session propagation

1. Record the client, CLIProxyAPI, and loaded plugin versions, and confirm the
   plugin is enabled. Restart the host after installation. A startup log is
   only a loading check.
2. Confirm the incoming request contains a stable per-conversation source from
   the [README priority table](../README.md#how-session-mapping-works).
   An existing `X-Opencode-Session` is authoritative and is not replaced,
   including when its value is invalid. A present but invalid or conflicting
   higher-priority source blocks fallback; fix the originating client.
3. If there is no source header, inspect the after-auth interceptor metadata.
   A valid `canonical_session_id` can be used then. The current code returns
   without mapping if `Headers` is null/absent; an empty headers map can still
   use metadata. With neither a usable source nor fallback, the plugin is a
   no-op. It does not mint an authenticated OpenCode identity.
4. On the credential/provider entry actually selected for the request, set:

   ```yaml
   headers:
     X-Opencode-Session: $X-Opencode-Session
     X-Opencode-Client: $X-Opencode-Client
   ```

   Check every applicable entry when credential rotation is enabled.
5. Use an isolated local mock upstream with synthetic prompts and dummy
   credentials, or sanitized outbound logging, to check the **wire request**.
   Verify the mapped session is present and stable across turns, and different
   real conversations have different IDs. Keep those IDs pseudonymized in
   reports. Do not send production credentials to a capture service.
6. If mapping succeeds but 403 remains, continue with API/access diagnosis.
   Do not repeatedly change session IDs or client labels as an authorization
   workaround.

The metadata fallback can collide for byte-identical independent conversations;
prefer a real client conversation ID. The last-resort `X-Client-Request-Id`
source only preserves affinity when that client actually uses a stable session
value there. A per-call request ID is not a stable conversation ID.

## Diagnose API/access failures

- Record the actual upstream host/path, model ID, and protocol after host
  translation, not just the downstream `/v1/...` URL.
- Compare them with the current official endpoint and model documentation.
  Check message/tool structure, streaming, and token limits separately from
  headers. The mapper neither reads nor fixes the body.
- Record whether access is keyless, API-key based, or through the official
  client, and which plan/provider is selected. Never include the key.
- Compare the proxy path with the documented direct API or official-client
  route using a synthetic prompt and the same model/access mode where
  supported. If only the proxy fails, inspect its translation and forwarding.
  If the supported direct route also fails, investigate upstream access,
  availability, or validation; session mapping alone cannot establish a fix.
- For a model/path that is not offered to the intended client, use the official
  supported client or a different authorized API/provider. Do not assume a
  successful third-party gateway replay establishes permission.

## Information to include in Issue #5

Please provide a **sanitized** minimal reproduction:

- Client, CLIProxyAPI, and loaded plugin version.
- Exact model ID and actual upstream URL/path.
- Access mode and plan, with credentials removed.
- Relevant plugin and credential `headers:` configuration.
- Source session-header names; whether the mapped header reaches upstream,
  and whether its pseudonymized value stays stable between turns.
- HTTP status, upstream error type/message, timestamp/time zone, and a request
  trace ID if safe to share.
- Whether the same model fails through the supported direct API or current
  official OpenCode client, including any custom-agent/tool configuration.

Remove API keys, cookies, authorization headers, personal prompts, and account
identifiers. Share schema/field names or a synthetic body instead of private
conversation content.

## Validation boundaries

This review compared the current repository code, existing tests, README,
gateway PR and code, official documentation, and upstream issue reports.
It did not run new live inference requests or reproduce the reporter's setup.
Existing `main_test.go` cases cover mapping, precedence, preservation,
metadata fallback, invalid input, and envelope handling; those tests do not
exercise OpenCode's free-tier authorization service.
